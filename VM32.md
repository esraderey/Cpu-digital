# Tramoya VM32

Tramoya VM32 es una máquina virtual RISC de 32 bits, determinista y embebible.
Está pensada para ejecutar lógica no confiable o extensible con límites claros,
no para emular eléctricamente una CPU física.

## Aplicaciones reales

- Lenguaje de scripting para videojuegos y simuladores.
- Reglas de negocio versionadas que no deben ejecutar Python arbitrario.
- Automatización determinista y reproducible.
- Plugins limitados por capacidades.
- Evaluación de código en ejercicios o retos.
- Contratos, flujos y agentes con presupuesto de ejecución.
- Lógica portable guardada como bytecode `.tvm`.
- Máquinas de control que deben pausar, esperar eventos y reanudarse.

No incorpora filesystem, red ni procesos como servicios predeterminados. Esas
capacidades solo pueden añadirse mediante syscalls explícitas del host.

## Capacidades

| Área | Implementación |
|---|---|
| Palabra | Entero con signo de 32 bits |
| Registros | 16 (`R0` cero, `R1..R14` generales, `R15` profundidad de pila) |
| Memoria | 1 048 576 palabras por defecto; configurable hasta 16 777 216 |
| ISA | 79 instrucciones de ancho fijo (4 palabras), 18 de ellas vectoriales TNU |
| Banderas | Zero, Negative, Carry y Overflow |
| Control | Saltos, llamadas, retorno, breakpoints y ejecución paso a paso |
| Pila | Protegida por límite configurable |
| FPU | IEEE 754 single-precision: `FADD`, `FSUB`, `FMUL`, `FDIV`, `FCMP`, `FTOI`, `ITOF`, `FABS`, `FSQRT` |
| Aritmética 64-bit | `MULH` (high32 de multiplicación), `ADDX`/`SUBX` (cadena de carry/borrow) |
| Fibras | Coroutines cooperativas: `SPAWN`, `SWITCH`, `FRET` (hasta 64 por defecto) |
| Interrupciones | 256 vectores, `INT`, `IRET`, `EI`, `DI` y cola externa |
| Host | Syscalls extensibles con políticas de capacidades |
| Recursos | Gas global, límite de pila, memoria, fibras y buffer de traza |
| Seguridad | Código de solo lectura, validación de PC/registros/memoria y rollback por instrucción |
| Persistencia | Snapshots paginados v2, compatibilidad v1 y bytecode con versión/CRC |
| Espera | Estado `WAITING`, entrada tardía y `YIELD` cooperativo |

## Ensamblador

Cada instrucción ocupa cuatro palabras: opcode y tres campos. Esto simplifica la
validación, el salto aleatorio y la interpretación segura.

```asm
.code
.entry _start

_start:
        LEA R4, NUMEROS
        MOVI R2, 0
        MOVI R3, 4

BUCLE:
        LOAD R5, [R4]
        ADD R2, R2, R5
        ADDI R4, R4, 1
        SUBI R3, R3, 1
        CMPI R3, 0
        JPOS BUCLE

        MOV R1, R2
        SYSCALL 1
        HALT

.data
NUMEROS: .WORD 10, 20, 30, 40
```

Directivas disponibles:

- `.code` / `.data`: secciones ejecutable y de datos.
- `.entry ETIQUETA`: punto de entrada.
- `.equ NOMBRE VALOR`: constante.
- `.word`: datos de 32 bits.
- `.string`: texto terminado en cero.
- `.space`: reserva palabras inicializadas en cero.
- `.align`: alinea la sección de datos a una potencia de dos.

Los operandos de memoria aceptan `[R4]`, `[R4+8]`, `[R4-2]` o `[ETIQUETA]`.

## Syscalls incluidas

| Número | Nombre | Convención | Capacidad |
|---:|---|---|---|
| 0 | `exit` | código en `R1` | ninguna |
| 1 | `print_int` | valor en `R1` | `io` |
| 2 | `print_char` | byte bajo de `R1` | `io` |
| 3 | `read_int` | resultado en `R1`; espera si no hay entrada | `io` |
| 4 | `memory_size` | resultado en `R1` | `introspection` |
| 5 | `cycles` | resultado en `R1` | `introspection` |
| 6 | `random` | PRNG determinista en `R1` | `random` |
| 7 | `print_string` | dirección `R1`, máximo `R2` | `io` |
| 8 | `alloc` | cantidad/resultado en `R1` | `memory` |
| 9 | `memory_chip_read` | offset bytes `R1`, destino RAM `R2`, cantidad bytes `R3`; devuelve bytes en `R1` | `memory_chip` |
| 10 | `memory_chip_write` | offset bytes `R1`, origen RAM `R2`, cantidad bytes `R3`; devuelve bytes en `R1` | `memory_chip` |
| 11 | `memory_chip_size` | capacidad en bytes en `R1` | `memory_chip` |
| 12 | `npu_info` | base de la ROM TNU en `R1`, palabras en `R2` | `npu` |

Las transferencias 9 y 10 copian como máximo 4 096 bytes por llamada. En una
lectura cada byte del chip se guarda en una palabra de RAM; en una escritura se
usa el byte bajo de cada palabra fuente. Las escrituras permanecen en el chip
aunque la VM se reinicie o se restaure un snapshot; el snapshot guarda la RAM de
VM32, no el contenido del chip.

Para habilitar el dispositivo en el CLI, conecta un archivo de chip:

```powershell
.\.venv\Scripts\python.exe tramoya_vm.py programa.tasm --memory-chip chips\flash_500mb.sqlite
```

La consola web local conecta por defecto `chips/flash_500mb.sqlite`. Si se usa
otra ruta, pásala con `--memory-chip`. En una integración Python se debe adjuntar
un `NonVolatileMemoryChip` y habilitar la capacidad `memory_chip` en `VMConfig`.

Ejemplo `.tasm` para leer los primeros 16 bytes del chip en palabras consecutivas
de RAM:

```asm
.code
.entry _start
_start:
    MOVI R1, 0
    LEA R2, BUFFER
    MOVI R3, 16
    SYSCALL 9
    HALT

.data
BUFFER: .SPACE 16
```

## Integración en Python

```python
from cpu_digital import TramoyaVM32, VM32Assembler

source = """
.code
    MOVI R1, 21
    SYSCALL 100
    SYSCALL 1
    HALT
"""

program = VM32Assembler().assemble(source).program
vm = TramoyaVM32()

def duplicar(machine: TramoyaVM32) -> None:
    machine.set_register(1, machine.get_register(1) * 2)

vm.register_syscall(100, duplicar, name="duplicar")
vm.load_program(program)
result = vm.run()
assert result.output == (42,)
```

Una syscall personalizada puede:

- Leer/escribir registros mediante `get_register()` y `set_register()`.
- Acceder a memoria validada con `read_memory()` y `write_memory()`.
- Emitir datos con `emit()`.
- Suspender con `wait_for_host()`.
- Finalizar mediante `terminate()`.

Si la syscall lanza una excepción, la VM pasa a `FAULTED` y revierte los cambios
de la instrucción, incluidas escrituras de memoria realizadas por la API.

## Interrupciones

Desde el host:

```python
vm.set_interrupt_vector(1, program.symbols["ISR_1"])
vm.request_interrupt(1)
vm.run()
```

Desde la CLI:

```powershell
.\.venv\Scripts\python.exe tramoya_vm.py --demo interrupcion --vector 1=ISR_1 --interrupt 1
```

El contexto interrumpido conserva PC, banderas, estado de habilitación y la fibra
interrumpida. `IRET` lo restaura y falla si se ejecuta desde otra fibra; la
profundidad está limitada para impedir desbordamientos.

## FPU — Punto flotante

Los registros almacenan floats IEEE 754 single-precision como enteros de 32 bits.
Las instrucciones FPU interpretan los bits como float, operan y escriben el
resultado reinterpretado. Las banderas después de una operación flotante:

| Bandera | Significado |
|---|---|
| Z | Resultado es ±0.0 |
| N | Resultado es negativo |
| C | Resultado es NaN |
| O | Resultado es ±infinito |

Las banderas describen el float32 realmente almacenado (tras el redondeo): un
desbordamiento a infinito activa `O` y un subdesbordamiento a cero activa `Z`.
El desbordamiento da ±infinito con cualquier versión del host: CPython 3.13
reciente lanza una excepción al empaquetar un float32 fuera de rango, y la VM la
convierte en el infinito del signo correspondiente.
Todo resultado NaN se guarda como el **NaN canónico** `0x7FC00000` (como en
RISC-V): la carga útil que propaga el host con dos operandos NaN depende del
orden de los operandos en el código máquina, y CPython lo cambia al especializar
la operación, así que conservarla haría que el mismo programa diera resultados
distintos según cuántas veces se hubiera ejecutado.
`FCMP` compara directamente sin restar: con algún NaN, `C=1` y el resto a 0; si no,
`Z` (iguales), `N` (`a < b`), `C=0` y `O=0`.

```asm
    MOVI R1, 0x40490FDB   ; π ≈ 3.14159f
    MOVI R2, 0x40000000   ; 2.0f
    FMUL R3, R1, R2       ; R3 = π × 2 ≈ 6.2832f
    FTOI R4, R3           ; R4 = 6 (truncado)
    ITOF R5, R4           ; R5 = 6.0f
    FSQRT R6, R2          ; R6 = √2 ≈ 1.4142f
```

## Aritmética de 64 bits

`MULH` devuelve los 32 bits altos de una multiplicación con signo de 64 bits.
Combinado con `MUL` (bits bajos), permite multiplicaciones completas de 64 bits.

`ADDX` y `SUBX` usan la bandera de Carry como acarreo/préstamo de entrada,
permitiendo sumas y restas encadenadas de precisión arbitraria:

```asm
    ; 64-bit: R2:R1 + R4:R3 → R6:R5
    ADD  R5, R1, R3       ; R5 = low + low (setea Carry)
    ADDX R6, R2, R4       ; R6 = high + high + Carry
```

## Fibras cooperativas

Las fibras son hilos cooperativos ligeros dentro de una misma VM. Cada fibra
tiene sus propios registros, banderas y pila, pero comparten la memoria y el
pool de gas.

| Instrucción | Descripción |
|---|---|
| `SPAWN dir` | Crea una fibra nueva en la dirección. Su ID queda en `R1`. |
| `SWITCH Rn` | Guarda el contexto actual y carga el de la fibra `Rn`. |
| `FRET` | Termina la fibra actual y regresa a la fibra padre. |

La fibra principal (ID 0) no puede terminar con `FRET`; debe usar `HALT`.
Las interrupciones solo se despachan en la fibra principal: una interrupción externa
queda en cola mientras corre otra fibra, e `INT` fuera de la fibra 0 es un fallo.
El límite de fibras es configurable (`fiber_limit`, por defecto 64) y cuenta solo
fibras vivas distintas de la principal: al ejecutar `FRET` la fibra se retira, así
que no consume límite y `SWITCH` hacia ella falla como fibra inexistente.

```asm
.code
_start:
    SPAWN worker       ; Crear fibra → ID en R1
    MOV R2, R1         ; Guardar ID
    SWITCH R2          ; Cambiar a la fibra
    ; ... al regresar de FRET, continúa aquí ...
    HALT

worker:
    MOVI R1, 42
    SYSCALL 1          ; Emitir 42 desde la fibra
    FRET               ; Regresar al padre
```

## Chip Neuronal Tramoya (TNU)

El TNU es un coprocesador vectorial conectado a VM32 tras la capacidad `npu`
(no incluida por defecto). Sin la capacidad, o sin chip conectado, **cualquier**
opcode TNU falla sin efectos. El invitado orquesta el modelo (capas, cabezas,
caché KV, muestreo, texto); el host solo ejecuta núcleos vectoriales en C
(`math.sumprod`, `memoryview`), sin dependencias nuevas. Requiere Python ≥ 3.12.

```python
from cpu_digital import TramoyaVM32, VMConfig
from cpu_digital.tnu import TensorROM, TramoyaNeuralUnit

rom = TensorROM.from_file("models/stories260K.trom")
vm = TramoyaVM32(
    VMConfig(capabilities=frozenset({"io", "memory", "npu"}), gas_limit=10**9, trace_size=0),
    npu=TramoyaNeuralUnit(rom),
)
```

### ROM de tensores

- Ventana fija de solo lectura `[0x40000000, 0x40000000 + palabras)`, separada de
  la RAM: `MAX_MEMORY_WORDS` no cambia y los pesos no ocupan RAM. `LOAD` (también en
  bucles acelerados) y `print_string` leen la ROM (con `npu`); `STORE` y cualquier
  destino TNU en ella fallan.
- `TensorROM` copia el archivo a memoria y calcula su sha256 al abrirlo: lo que se
  usa es exactamente lo que se ha medido.
- Los snapshots **no** copian la ROM: guardan `{"sha256", "size_bytes", "path"}`.
  Restaurar exige que el host haya conectado una ROM con la misma huella; la ruta
  del snapshot (solo el nombre del archivo) es informativa y **nunca se abre**.
  `from_snapshot_bytes(..., npu=...)`. El cotejo de huella evita restaurar por error
  sobre otra ROM; no autentica el snapshot (quien lo fabrica puede omitir la clave,
  igual que puede fabricar la RAM).
- Syscall 12 `npu_info` (capacidad `npu`): `R1` = base de la ROM, `R2` = palabras.

### Modelo de ejecución vectorial

`VCFG Ra, Rb, Rc` fija `VL` (longitud o columnas, 1..2²⁴), `VR` (filas, 0..2²⁴) y
`VS` (paso entre filas en palabras; 0 = denso, igual a `VL`). Es estado del núcleo
compartido por las fibras (como la memoria), entra en el snapshot (`core.tnu`,
solo si difiere de 0,0,0) y se revierte con el registro de deshacer. Los
operandos son registros con direcciones; cada región debe caer entera en la RAM o
entera en la ROM.

| Opcode | Forma | Semántica (f32 salvo indicación) | Unidades de trabajo |
|---|---|---|---|
| `VCFG` | `Rl, Rr, Rs` | `VL, VR, VS ← Rl, Rr, Rs` | — |
| `VCOPY` | `Rd, Ra` | copia `VL` palabras (ROM→RAM o RAM→RAM) | VL |
| `VADD`/`VMUL` | `Rd, Ra, Rb` | elemento a elemento | 2·VL |
| `VSCALE` | `Rd, Ra, Rs` | `[Rd] = [Ra] · f32(Rs)` | 2·VL |
| `FDOT` | `Rd, Ra, Rb` | `Rd = f32(Σ a·b)`; banderas FPU | VL |
| `MATVEC` | `Rd, Rw, Rx` | `out[r] = Σ_j W[r·VS+j]·x[j]`, `VR` filas | max(VR·VL + 8·VR, región) |
| `MATTV` | `Rd, Rw, Ra` | `out[j] = Σ_r a[r]·W[r·VS+j]`, `VL` columnas | max(VR·VL + 8·VL, región) |
| `RMSNORM` | `Rd, Ra, Rw` | `w ⊙ a / √(mean(a²)+1e-5)` | 3·VL |
| `VSOFTMAX` | `Rd, Ra` | softmax (máximo restado, suma con `fsum`) | 5·VL |
| `VEXP`/`VSILU` | `Rd, Ra` | `exp` (desbordamiento → +inf), `x·σ(x)` (→ −0 para x muy negativo) | 4·VL |
| `ROPE` | `Rv, Rp, Rh` | RoPE de llama2.c in situ, posición `Rp`, cabeza `Rh` (par, ≤ 256, divide a VL) | 4·VL |
| `VARGMAX` | `Rd, Ra` | primer índice del máximo (con NaN, determinista pero dependiente de su posición) | 2·VL |
| `VSAMPLE` | `Rd, Ra, Rc` | primer `i` con `Σ_{≤i} p > f32(Rc)` (recorrido lineal, vale con cualquier contenido); si no, `VL-1` | 2·VL |
| `VQUANT` | `Rd, Ra` | vector Q8: `VL` bytes `q+128` y escala f32 (`VL/4 + 1` palabras) | 3·VL |
| `QMATVEC` | `Rd, Rw, Rx` | matriz Q8 (`VR·VL/4` palabras de bytes + `VR` escalas) × vector Q8 | VR·VL + 8·VR |
| `QROW` | `Rd, Rw, Rr` | fila `Rr` de una matriz Q8 descuantizada | 2·VL |

**Numérica declarada.** Cada resultado se calcula en doble precisión y se redondea
**una vez** a float32 al guardarse. `VADD`, `VMUL` y `VSCALE` coinciden bit a bit
con `FADD`/`FMUL`, salvo en la carga útil de un NaN. `FDOT`/`MATVEC`/`MATTV` acumulan con `math.sumprod` (precisión
extendida): son deterministas, pero **no** iguales a una cadena de `FMUL`+`FADD`.
Q8 usa cuantización simétrica (`round` al par más cercano, escala float32 por
fila o por vector) y productos enteros exactos. `exp`, `cos`, `sin` y `pow` vienen
de la libm del host: el resultado es determinista en una misma plataforma; la
igualdad bit a bit entre sistemas operativos no está garantizada.

**Gas.** Coste base de la ISA (1 para `VCFG`, 2 para el resto) más
`ceil(unidades / 64)`. El gas se comprueba y se cobra antes de leer o calcular;
una instrucción está limitada a 2²⁶ unidades. La calibración (µs por gas de cada
operación frente al intérprete) está en `RFC-EXP-00016.md` §P5.

**Atomicidad.** Orden fijo: permisos → parámetros → tope → gas → lectura →
cálculo → una sola escritura. La escritura guarda antes el contenido previo en el
registro de deshacer, invalida la caché de decodificación si toca código (con
`protect_code=False`) y falla si el destino es código protegido o la ROM.

## Acelerador de bucles

`run()` compila los bucles internos calientes a funciones Python y ejecuta sus
iteraciones sin la sobrecarga por instrucción del intérprete (checkpoint,
dispatch, traza). El contrato es que el estado observable sea **idéntico** al
del intérprete: cada instrucción se genera con su misma aritmética, sus mismos
redondeos y sus mismas banderas; el gas y el presupuesto de instrucciones se
comprueban por vuelta, contra la vuelta más larga; y antes de cada instrucción
que podría fallar se comprueba que no falle. Si algo pudiera fallar (lectura
fuera de la RAM y de la ROM legible, escritura en código, en la ROM o fuera de
rango, divisor cero, raíz negativa, conversión imposible, pila llena o vacía), la
función devuelve el control al intérprete **en esa instrucción**, con el estado
parcial escrito, y el intérprete la ejecuta con su validación, su mensaje y su
rollback.

- Se acelera un bucle cuando su cabecera ha recibido 32 saltos hacia atrás
  (`LOOP_WARMUP`). Su cuerpo va de la cabecera al primer salto que vuelve a
  ella (hasta 64 instrucciones) y puede contener `MOV`,
  `MOVI`, `LEA`, `LOAD`, `STORE`, aritmética entera (con `DIV` y `MOD`), lógica,
  desplazamientos, `CMP`/`CMPI`/`TEST`, `PUSH`/`POP`, `FADD`, `FSUB`, `FMUL`,
  `FDIV`, `FSQRT`, `FABS`, `FCMP`, `FTOI`, `ITOF` y `NOP`, además de saltos hacia
  delante: dentro del cuerpo (if/else, continue) o fuera de él (salidas
  anticipadas; la última instrucción registrada es entonces ese salto).
  Llamadas, syscalls, saltos hacia atrás distintos del de vuelta (bucles
  anidados), fibras, TNU y el resto de instrucciones lo dejan en el intérprete.
- `LOAD` lee la RAM y, fuera de ella, la ROM del TNU con la misma regla que el
  intérprete (capacidad `npu` y un TNU con ROM). La ROM se consulta en cada
  entrada al código compilado, así que conectar, cambiar o desconectar el TNU
  entre dos `run()` no exige recompilar. Con subclases de `TramoyaNeuralUnit` o
  de `TensorROM`, o si las capacidades no son un `frozenset`, que podrían
  responder distinto a cada consulta, esa lectura la hace el intérprete: el
  bucle compilado le devuelve el control en ella.
- Se desactiva con traza (`trace_size > 0`), con breakpoints, con interrupciones
  pendientes, con `VMConfig(accelerate_loops=False)` o con
  `--no-loop-acceleration` en el CLI. `step()` nunca lo usa. El CLI y la consola
  activan la traza por defecto (4 096 entradas): para acelerar en el CLI hay que
  pasar `--trace-buffer 0`.
- Tampoco actúa si una subclase o la propia instancia sustituyen un manejador
  `_op_*` o un método del que depende el código generado (`_execute_one`,
  `_push`, `_add`, `write_memory`, `_read_rom_word`…): el código compilado
  reproduce la semántica de `TramoyaVM32` y no la de la extensión.
- Compilar cuesta de ~0,3 ms a ~8 ms según el cuerpo y el gas no lo cobra, así
  que se paga con instrucciones ejecutadas: cada intento de compilación aplaza
  el siguiente 1 024 instrucciones, más 256 por instrucción del bucle compilado
  (`LOOP_COOLDOWN` y `LOOP_COOLDOWN_PER_INSTRUCTION`). La espera es de la VM, no
  de cada cabecera; un intento fallido paga la parte fija, y mientras dura, un
  bucle caliente sigue en el intérprete. Las instrucciones de una entrada al
  bucle compilado cuentan doble, todas, si esa entrada ejecuta al menos tantas
  como tiene el bucle: un bucle que se usa se paga antes, y uno que sale del
  cuerpo nada más entrar, no. Así, lo que un programa puede hacer gastar al
  host compilando queda acotado por lo que ejecuta, escriba o no en su código.
  Solo la primera compilación tras cargar un programa o restaurar un snapshot
  se hace sin haber pagado nada.
- Escribir código (`protect_code=False`) invalida los bucles compilados y
  reinicia el calentamiento: cada cabecera vuelve a necesitar 32 saltos hacia
  atrás sobre el código nuevo, y compilarla otra vez se paga como cualquier
  otra compilación.
- Una excepción asíncrona del host (Ctrl+C) dentro de un bucle acelerado deja
  memoria y pila por delante de registros, pc y contadores: tras ella no se debe
  reanudar la VM ni guardar un snapshot. El intérprete tampoco revierte la
  instrucción en curso ante una excepción así, pero el acelerador amplía el daño
  a todas las vueltas de esa llamada.
- `accelerated_instructions` cuenta las instrucciones que ejecutó el acelerador
  (incluidas en `instructions`).

Medido (Python 3.13.2, Windows x64, `benchmarks/benchmark_vm32.py`): el bucle
`ADDI`+`JMP` pasa de ~557 000 a ~5,5 M instr/s; un producto punto escalar
(`LOAD`, `LOAD`, `FMUL`, `FADD`, dos `ADDI`, `SUBI`, `JNZ`) de ~55 000 a ~345 000
MAC/s. Los programas cortos y los bucles con llamadas o syscalls no cambian. Con
los pesos en la ROM del TNU, ese producto tarda 0,14–0,15 veces lo que en el
intérprete, igual que con ellos en la RAM (`benchmarks/benchmark_rom.py`). Hasta
el 2026-10-02 el código compilado devolvía el control en cada lectura de la ROM,
y con ella al principio del cuerpo el bucle tardaba de 1,16 a 1,27 veces lo que
sin acelerador. `vm_programs/llama2.tasm` no cambia: no compila ningún bucle
(los suyos llevan `CALL` u operaciones TNU) y sus lecturas de la ROM con `LOAD`
quedan fuera de bucles compilados.

En código de juego lo mide `benchmarks/benchmark_cobertura.py` sobre
`vm_programs/juego_raycaster.tasm`, un raycaster de 160×120 con 16 entidades,
colisiones, sprites con z-buffer y minimapa, escrito por un autor que no conocía

instrucciones se ejecuta en bucles compilados y el programa corre 3,2 veces más
rápido, con el mismo estado final; con cuerpos solo lineales (la primera

## Memoria paginada y rendimiento

La RAM es lógica y dispersa: se divide en páginas de 4 096 palabras (16 KiB) y
solo materializa las páginas que reciben datos. La configuración predeterminada
expone 1 048 576 palabras (4 MiB lógicos), mientras que el máximo es 16 777 216
palabras (64 MiB lógicos). Un programa pequeño normalmente reserva una sola página.

La ejecución continua usa una ruta por lotes que conserva las transiciones finales
de Tramoya y la traza por instrucción, pero evita un `self-loop` de la máquina de
estados por cada opcode. `step()` conserva el camino totalmente instrumentado.

El código protegido se decodifica una vez al cargar. Si `protect_code=False` y una
escritura modifica una instrucción, la entrada afectada de la caché se invalida.
Los snapshots v2 guardan únicamente páginas no vacías y pueden restaurar snapshots
densos v1. La restauración es atómica: se valida todo el snapshot antes de tocar la VM.
`TramoyaVM32.from_snapshot_bytes()` nunca adopta las capacidades embebidas en el
snapshot (usa `capabilities=` o las de `VMConfig()`), y con `limits=` rechaza
snapshots cuyos límites de recursos superen los del host.

## Ciclo de vida Tramoya

```mermaid
stateDiagram-v2
    CREATED --> READY: load
    READY --> RUNNING: start
    RUNNING --> RUNNING: tick interno
    RUNNING --> PAUSED: pause / BREAK
    PAUSED --> RUNNING: resume
    RUNNING --> WAITING: YIELD / read_int
    WAITING --> RUNNING: wake / entrada
    RUNNING --> HALTED: HALT / exit
    RUNNING --> FAULTED: validación o recurso agotado
```

Tramoya controla transiciones, hooks, historial de ciclo de vida, observabilidad,
rollback de callbacks, serialización del estado de control y exportación Mermaid.
`step()` usa la transición interna; `run()` ejecuta el bloque dentro de `RUNNING` y
solo dispara transiciones cuando cambia el ciclo de vida. La memoria y los registros
mantienen rollback por instrucción sin copiar toda la RAM.

## Modelo de seguridad

- El programa solo puede ejecutar direcciones alineadas dentro de `.code`.
- `STORE` no puede modificar código cuando `protect_code=True`.
- Registros, memoria, pila, destinos y vectores se validan en runtime, incluso
  cuando el bytecode no procede del ensamblador.
- Cada instrucción tiene coste de gas antes de ejecutarse.
- Una instrucción fallida revierte registros, flags, pila, E/S y escrituras RAM.
- Las escrituras del chip son persistentes, se confirman como transacción y no
  se revierten con una restauración de RAM o snapshot.
- Las syscalls están sujetas a capacidades del host.
- No hay acceso implícito a Python, disco, red, variables de entorno o procesos.
- El CRC detecta corrupción accidental; no sustituye una firma criptográfica.

Una syscall personalizada es código Python confiable del host. Si expone disco o
red, esa autoridad pertenece al host y debe diseñarse de forma explícita.

expectativas antes de tocar el núcleo; se cerró el 2026-10-10. Lo que sigue es HECHO

### E1: cuántas instrucciones cuesta arrancar Linux nommu, y cómo son sus bloques

### E2: carriles de bytes sobre la memoria paginada y anillo de deshacer

`benchmarks/benchmark_rv32_memoria.py` mide, sobre `PagedMemory` sin tocarla, dos

`array('i')`. Cada acceso comprueba el rango y resta la base `0x80000000`. Las cifras

Veredictos de E2 (umbrales del RFC §5): la vía que describe el texto de P1.1 queda en

tres versiones y sobrevive con holgura. Las medias palabras por vista quedan en
1,34–1,51× y la palabra desalineada en ~2×; el RFC no les fija umbral (son
decisiones de la implementación). El anillo que deshace instrucciones está en el
umbral del 25 % en 3.13 y 3.12 y por encima en 3.10 (cota superior, porque el
intérprete mínimo no decodifica desde memoria ni atrapa): se retira y queda snapshot
más reejecución, como ya proponía P1.10; el anillo de solo escrituras es barato pero
no tiene uso en el diseño de comprobar-y-confirmar.

**Decisión del 2026-10-10 (P1.1 y P1.10 enmendados en el RFC).** Antes de redactar
P1.1 con vistas por página se buscó una alternativa que anulara sus desventajas (caché
de vistas que reconstruir al restaurar, materialización a mano, página ausente y
cruce de página en el camino caliente, granularidad de 16 KiB): la RAM del hart entera
en un `mmap` anónimo, con tres vistas `B`/`I`/`i` sobre el único búfer y un mapa de
bits de páginas de 4 KiB escritas que cada `store` marca. El sistema operativo
materializa cada página al tocarla (0 MiB residentes al crear 64 MiB; +8,1 MiB tras
escribir 1 900 páginas al azar; un `bytearray` de 64 MiB compromete los 64 MiB al
crearse), las vistas son función del búfer (nada que inventariar en P2.5), no hay
páginas ausentes ni cruces, y el snapshot guarda solo las páginas marcadas (exacto
mientras toda escritura pase por la capa; un escaneo completo costaría 125 ms y
comprometería toda la RAM). Medido con `--plana` (mismo protocolo; la RAM contigua
incluye el mapa de bits en cada `store`, que las vistas por página no llevan y
necesitarían igual para la generación de P1.6):

| RAM contigua / vistas por página (neto) | 3.13 | 3.12 | 3.10 |
|---|---|---|---|
| `lw` / `lb` / `lbu` | 0,73× / 0,65× / 0,59× | 0,78× / 0,69× / 0,64× | 0,65× / 0,60× / 0,53× |
| `lh` / `lhu` / `lw` desalineada | 0,71× / 0,72× / 0,77× | 0,77× / 0,74× / 0,77× | 0,70× / 0,63× / 0,70× |
| `sw` / `sb` / `sh` (con mapa de bits) | 0,98× / 0,93× / 1,06× | 0,97× / 0,95× / 1,09× | 0,88× / 0,92× / 1,08× |

Lo que no anula: la hipótesis de host little-endian con palabras de 4 bytes (se
comprueba al arrancar) y la regla de que el host escriba en la RAM del hart solo por
la capa; añade liberar las vistas antes de cerrar el `mmap` y que la memoria residente
crezca también con las lecturas, acotada por la RAM. Se eligió esta alternativa.

**No cubierto por H0.** E1 mide una sola imagen (6.1.14 nommu de cnlohr, 64 MiB) y
solo hasta el prompt, con el emulador de referencia, no con el hart; las entradas en
`mtvec` se estiman por el `pc`; la CI no compila `contar.c` ni ejecuta E1 (necesita
clang y las descargas), aunque sí comprueba los sha256 de los binarios. E2 es un
microbanco, no el intérprete real: no mide materializar páginas al vuelo ni fallos de
la caché de vistas, solo un tamaño de anillo (4 096), sin CSR en el anillo, con la
máquina al 0–10 % de carga y con CPython 3.13.2, no el 3.13.15 de la CI.

### H2: snapshot del hart, invariante S y conformidad (E4, E5)

H2 empieza por el refinamiento de P1.6 que H1 dejó medido como PROPUESTA; los pasos
siguientes (snapshot y restauración del hart, invariante S bajo cortes, riscv-tests y
ACT4) se documentan en este mismo apartado a medida que cierran. Todo lo que sigue es HECHO
salvo lo marcado.

**H2.0: mapa de líneas de código de 16 bytes (enmienda de P1.6, aprobada el 2026-10-11,
integrada el 2026-10-12).** La invalidación por generación de página de 4 KiB hacía que
cualquier store a datos que compartieran página con el código caliente invalidara sus bloques
(y la caché de decodificación de la página): con Embench enlazado con los datos pegados al
código, la media geométrica bajaba de 3,30× a 2,66× y huffbench a 1,03×. Antes de tocar el
código se reinvestigó el prototipo de H1 en reposo, con dos rondas (Embench) y tres (CoreMark)
y cinco tamaños de línea (`.forja/h2/investigacion-p16.md`, evidencia en
`.forja/h2/reinvestigacion-p16/`): con líneas de 64 y 32 bytes `ud` seguía al 85,5 % de
cobertura porque su variable caliente `chkerr` está a 20 bytes del fin de `.text`; con 16
bytes los 14 benchmarks empaquetados igualaban al alineado (3,38× frente a 3,33×); con 8
bytes no se ganaba nada (3,39×) y el mapa doblaba su tamaño. En los 14 binarios, con 16
bytes, un solo store de 3,35 millones cae en una línea de código (la escritura única de
`seed` en `ud`). Decisión del usuario: 16 bytes.

Diseño (`cpu_digital/rv32_mem.py`, `rv32_hart.py`, `rv32_blocks.py`; especificación en
`.forja/h2/spec_p16_lineas_codigo.md`): `Rv32Memory` separa tres estados derivados.
`written` (un byte por página) dice si la página recibió alguna escritura desde la creación
o el último `reset` y es lo único que el snapshot mira (invariante: byte ≠ 0 ⇒ página
escrita); `code` (un byte por línea de `LINE_BYTES` = 16, la única constante que fija el
tamaño) dice si alguna palabra de la línea entró en una caché derivada (el hart la marca al
decodificar y `compile_block` marca las líneas del bloque antes de usarlo); `generations`
(monótonas) sube solo con los stores del invitado que tocan una línea marcada (todas las
páginas que el store toca), con toda escritura del host (`load_bytes`, `fill`,
`restore_pages`, `reset` sobre las páginas que borra) y con `clear_code`, que al desmarcar
sube la generación de las páginas que tenían marcas para que ninguna caché construida antes,
de este hart ni de otro que comparta la memoria, sobreviva al vaciado. En el hart, `sb`/`sw`
y el `sh` que no cruza línea marcan `written` y suben la generación solo si la línea tiene
código; el `sh` que cruza línea va por la vía lenta, que mira las dos líneas y sube las dos
páginas si hace falta. En los bloques, la guarda de store deja de ser «página propia» y pasa
a ser «línea sin código» (`not code[o >> 4]`), con `written[o >> 12] = 1` en vez de
`gens[o >> 12] += 1`: un store sobre una línea con código sale al intérprete, que invalida
como hoy. Nada cambia en la semántica del invitado, en el formato de snapshot v2 ni en VM32.

**No cubierto por H2.0.** El mapa se materializa entero al crear la memoria (RAM/16: 4 MiB

(correcto, más lento; no ocurre en CoreMark ni en Embench). Varios harts sobre una misma
memoria son coherentes, pero cada vaciado del mapa de uno cuenta como una invalidación para los
bloques de los demás y consume su tope de recompilaciones; `Machine` tiene un solo hart. El
coste de compilar sigue sin cobrarse a gas (P3). Las cifras son de una máquina con CPython
3.13.2.

**H2.1: snapshot y restauración del hart (P2.5, P2.3; integrado el 2026-10-19).** `Rv32Hart.snapshot()`
devuelve el estado arquitectónico y el contenido de la RAM en un diccionario serializable en JSON: registros,
`pc`, `instret` (64 bits; `run` envuelve el contador al terminar y `time`, `timeh` y `mtime` se calculan sobre el
contador envuelto, como los contadores de Zicntr), `csrs` (vacío en H2: los contadores se derivan de `instret` y
del divisor; H3 añade los de modo M con claves `"0x300"`), `reservation` (`null` hasta H3), `time_divisor`
(estado del invitado: fija `time` y `mtime`; el constructor solo admite [1, 2⁶⁴), el dominio del snapshot) y las
páginas escritas en el formato paginado v2 de VM32 con la geometría de la RAM; `Machine.snapshot()` añade el UART
(salida y cola de entrada) y `mtimecmp`. No lleva el gas (lo fija el arnés en cada `run`), ni la configuración
(`accelerate`, `horizon`, `warmup`, `max_blocks`, `keep_block_sources`, el bus), ni las cachés ni las estadísticas.
`restore` valida todo antes de tocar nada (claves exactas por nivel, tipos estrictos, rangos, `x0 = 0`, geometría de
la RAM igual a la conectada, páginas validadas por `restore_pages`; toda lista se copia antes de validarse y cada
valor se lee del diccionario una sola vez, de modo que lo validado es exactamente lo que se restaura aunque el objeto
cambie entre lecturas) y lanza `ValueError` dejando la máquina intacta; al confirmar vacía la caché de decodificación,
los bloques, el calentamiento, las recompilaciones y el mapa de código (`clear_code` sube la generación de las
páginas marcadas y `restore_pages` la de las restauradas y borradas, así que ninguna caché anterior, de este hart o
de otro sobre la misma memoria, puede coincidir), conserva la lista `regs` y la cola del UART (como `reset`) y no
toca la configuración, el gas ni las estadísticas. `state_hash()` es el sha256 de la serialización canónica del
snapshot (claves ordenadas, sin espacios), estable entre procesos: con él el arnés de E4 compara máquinas sin
igualar diccionarios. `snapshot_bytes()` / `restore_bytes()` / `Machine.from_snapshot_bytes()` envuelven el JSON con
la receta de VM32 (firma `RV32S\x01`, zlib de nivel 9, tope de 256 MiB descomprimidos, rechazo de flujos truncados o
con bytes de más; `from_snapshot_bytes` crea la máquina con la geometría del snapshot, rechaza una RAM mayor que
`max_ram_bytes` (64 MiB por defecto) antes de reservarla y cierra la máquina si la restauración falla por cualquier
causa, incluida una interrupción). `Machine` recuerda el divisor con que se construyó y `load_flat` lo repone (un
`restore` adopta el del snapshot); `Uart.reset` sustituye la salida por un `bytearray` nuevo, así que una vista
exportada por el host no deja la máquina a medias.

Puerta de inventario (P2.5): cada clase con `__slots__` de los módulos `rv32_*` (`Rv32Hart`, `Rv32Memory`, `Uart`,
`Clint`, `Bus`, `Syscon`, `Machine` y `Block`) declara `STATE_FIELDS` (entran en el snapshot), `DERIVED_FIELDS`
(campo → regla de invalidación, con palabras), `CONFIG_FIELDS`, `STATS_FIELDS` y `HARNESS_FIELDS` (`gas`); las
pruebas descubren los módulos `rv32_*` con `pkgutil` y las clases con slots (también vacíos) por introspección,
exigen que cada slot esté en exactamente una lista con su regla, fijan la clasificación exacta de cada campo,
comprueban que las instancias no tienen `__dict__`, que toda subclase de una clase inventariada declara sus slots,
que ninguna clase inventariada tiene atributos de clase de tipo mutable y que cada campo de estado del hart,
perturbado, aparece en el snapshot y cambia el hash: un slot nuevo sin clasificar, un módulo nuevo sin listar o un
campo de estado nuevo sin su perturbación ponen la suite en rojo. Lo que la puerta no ve (límite de una puerta
declarativa, medido por la ciega 3 con siete evasiones): estado fuera de los slots (una variable de módulo, un
cierre, un atributo de clase inmutable reasignado, un dispositivo definido en otro módulo adjunto al bus) y el uso
semántico de un campo clasificado como estadística o derivado; de esas evasiones, las pruebas de la invariante S
cazaron las que `run` leía (cuatro de siete) y las otras tres (dispositivos nuevos con estado) solo las ve la
revisión de cada paso: un dispositivo con estado tendrá que entrar en `Machine.snapshot` y en el inventario en H3.

Precondición de la invariante S: `run` con gas exacto (`horizon=True`, el valor por defecto). Sin horizonte, cuánto
rebasa cada `run` depende de qué bloques estén compilados y de los contadores de calentamiento, que no son estado
del invitado.

Pruebas (`tests/test_rv32_snapshot.py`, 62): ida y vuelta por diccionario, bytes y constructor; máquina usada con

**Propuesta: `accelerate=True` por defecto (PROPUESTA; la decide el usuario).** Con la invariante S probada con
bloques en E4 y E5 (0 divergencias con bloques, calentamiento 1 y 2, destino nuevo, usado y sonda entera), el RFC
pide proponer la activación por defecto con la cifra. Cifra: los bloques con horizonte van 3,23× (CoreMark) y 3,37×
(Embench empaquetado, media geométrica) más rápido que el intérprete con gas exacto (H2.0), el horizonte cuesta del 1
al 3 % frente a los bloques sin él (H1), y una restauración cuesta recompilar los puntos calientes del tramo
siguiente (23,4 compilaciones por restauración en CoreMark con calentamiento 1 y cortes uniformes, 9,4 con
sesgados; de 4 a 428 en Embench según el programa; la cobertura no baja con 1 000 cortes). Lo que no cambia con el valor por defecto: la semántica
del invitado, el gas, el formato de snapshot y los tests, que ya ejecutan los dos modos. Hasta la decisión,
`accelerate=False`.

**No cubierto por H2.1–H2.4.** El hash incremental por store de P2.3 (opcional, solo diagnóstico) no se implementó.
El bus y sus dispositivos no entran en el snapshot (H3 lo extenderá con las interrupciones del CLINT). `horizon=False`
queda fuera de la invariante S por diseño. El perfil clasifica como MMIO solo los accesos que cambian el estado del
dispositivo (una lectura de `mtime` o del LSR sale del bloque y cuenta como salida lenta) y no sitúa el evento dentro
de la ventana de 64 instrucciones de los programas grandes. rv32um/ua/mi y ACT `privilege` llegan con H3 (M, A,
Zicsr, traps). Los tiempos por corte son de una máquina con CPython 3.13.2; los recuentos son deterministas. `WFI` y
`mtimecmp` como eventos de temporizador llegan con H3.
## Límites honestos

VM32 ya es utilizable como runtime embebido, pero no es una CPU física, un sistema
operativo ni una sandbox aislada a nivel de proceso. Es de un solo hilo lógico
(las fibras son cooperativas, no paralelas), no tiene JIT ni recolector de basura.
Para ejecutar código adversarial de alto riesgo conviene además colocar el proceso
Python dentro de un contenedor o sandbox del sistema operativo.
